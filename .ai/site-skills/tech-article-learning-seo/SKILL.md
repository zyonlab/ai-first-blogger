# 技术文章教学化、证据化与 SEO 写作

## 目标

把技术知识组织成读者能沿着清晰路径理解、实践、验证并判断边界的内容，同时让搜索系统准确理解页面主题。

模仿只发生在抽象层：结构、节奏、解释顺序、例子密度、难度曲线和信息组织。不要复制参考文章的句子、独特比喻、故事、代码、案例、数据或标志性标题。

“自动检查通过”只表示未发现工具能识别的形式风险，不代表技术事实正确、引用语义匹配或目标读者已经看懂。

## 站点级 Hook 合同

本 Skill 是用户配置的写作策略，不是 AI First Blogger 的框架默认规则。由 `content-plans/site-plan.yaml` 注册，由 `content-plans/content-pipeline.yaml` 在对应阶段调用。

- `topic_research.after`：补充读者问题、证据等级、认知风险和原创价值锚点。
- `series_planning.before/after`：先约束终点能力、认知预算和搜索边界，再审计篇间依赖与连续性。
- `article_brief.before/after`：建立写作契约，并补齐知识阶梯、证据计划、认知预算和 SEO 发布要求。
- `draft.before/after`：按 brief 选择教学结构，成稿后检查例子、边界、证据标记和理解检查。
- `teaching_review.before/after`：应用认知负荷、渐进披露、worked example 和读者验证规则。
- `human_edit.after`：在不伪造作者经历的前提下，删除模板腔，保留具体判断、限制和取舍。
- `seo_geo_optimization.before/after`：先确认搜索意图和实体边界，再审计标题、摘要、内链、直接答案和来源表达。
- `publishing_review.before`：运行适用的结构、证据和系列检查，并准确报告验证范围。

不得覆盖框架的来源真实性、文件范围、内容 Schema、草稿状态、构建门禁、分支策略、密钥和部署权限。Hook 与框架规则冲突时，以框架规则为准。

## 何时使用

根据任务选择一种主模式：

- `analyze`：分析参考文章，输出可复用的风格画像。
- `plan`：生成单篇文章 brief、认知预算、知识依赖和大纲。
- `write`：从主题或 brief 写成完整文章。
- `rewrite`：保留事实与观点，重构现有草稿的教学性、证据链和 SEO。
- `series-plan`：设计系列地图、篇章依赖、难度递进、搜索边界和内链图。
- `series-write`：撰写系列总览页及指定批次或全部文章的完整正文，并维护篇间连续性。
- `series`：兼容别名；“规划系列”路由到 `series-plan`，“写成系列”路由到 `series-write`。
- `audit`：对文章或系列做技术、教学、认知预算、证据语义、连续性、原创性和 SEO 审计。

用户未指定模式时，根据交付目标自动选择；“写一篇”用 `write`，“设计/规划系列”用 `series-plan`，“写系列/完成系列正文”用 `series-write`，“看看哪里不好/测试质量”用 `audit`。

- 面向小白、长文或需要验证理解：再读取 [references/cognitive-validation.md](references/cognitive-validation.md)。
- 需要选择文章结构：读取 [references/content-patterns.md](references/content-patterns.md)。
- 需要核验引用、实验、性能或高风险主张：读取 [references/evidence-validation.md](references/evidence-validation.md)。
- 需要 SEO、标题、摘要、内链或生成式搜索优化：读取 [references/seo-playbook.md](references/seo-playbook.md)。
- 需要规划系列：读取 [references/series-architecture.md](references/series-architecture.md)。
- 需要把系列逐篇写成完整正文：同时读取 [references/series-writing.md](references/series-writing.md)。
- 输出前审计：读取 [references/qa-rubric.md](references/qa-rubric.md)。

可复用模板位于 `assets/`。单篇完成后可运行：

```bash
python scripts/article_lint.py <article.md> --report
python scripts/evidence_lint.py <evidence-ledger.json> --article <article.md>
```

系列完成后再运行：

```bash
python scripts/series_lint.py <series-dir>
```

这些脚本只提供结构、预算和可追踪性检查，不能替代技术审阅、来源语义审阅或真实读者测试。

## 默认假设

缺少非关键输入时不要阻塞，明确写出假设并继续：

- 语言：跟随用户语言。
- 读者：默认 `beginner_engineer`；用户写“小白、零基础、不懂编程、通俗入门”时自动使用 `absolute_beginner`。
- 深度：从完成当前承诺所需的最短路径开始，再用渐进披露提供可选机制与进阶内容。
- 认知预算：普通入门解释默认 `8-12m`、`math_budget:intuitive`、`code_budget:minimal`；绝对小白默认 `code_budget:none`，除非任务要求动手。
- 搜索意图：信息获取或问题解决。
- 证据等级：普通技术文章默认 `standard`；稳定低风险背景可用 `light`；高风险、争议或性能结论用 `rigorous`。
- 证据优先级：官方文档、标准、论文、源码、可复现实验，其次是可信工程实践。
- 示例：使用一个贯穿全文、可运行或可观察的最小案例。
- 理解度状态：没有真实测试记录时默认为 `not_run` 或 `self_check_only`，不得声称目标读者已经验证能看懂。

只有当缺失信息会改变技术结论、目标读者或交付形态时，才提出少量关键问题；否则自行作出可逆假设。

## 不可妥协的规则

1. 技术正确性高于文风相似度，读者完成目标高于关键词覆盖率。
2. 将事实、推断、经验建议和个人选择明确区分。
3. 可能变化的版本、价格、API、法规、性能结论和生态状态必须核验当前一手来源。
4. 不编造亲身经验、实验、指标、引用、故障记录、读者反馈或用户测试。
5. 不用关键词密度、固定字数、批量长尾页面或“AI 搜索黑科技”代替内容价值。
6. 每个重要结论都要回答：为什么成立、如何验证、在什么条件下不成立。
7. 参考文章中的事实与观点需要追溯原始来源；参考文章只用来学习表达机制。
8. 认知预算是写作契约：超出术语、时长、数学或代码预算时，必须删减、桥接、分层或拆篇，并说明理由。
9. 引用链接存在不代表语义支持；核心主张必须检查同义支持、范围、强度和例外。
10. 自动 linter、作者自测和真实读者测试必须分开报告；不得用一个替代另一个。

## 工作流

### 1. 建立写作契约

先形成一个紧凑的 content brief，至少包含：

- 目标读者等级、已有知识和常见误解；
- 阅读后能完成的具体任务或能回答的具体问题；
- 前置知识、范围和非目标；
- 阅读时长、核心术语、数学、代码和难度跳跃预算；
- 主搜索意图与读者真正想解决的问题；
- 内容类型：教程、操作指南、原理解释、参考、排障、比较或案例研究；
- 技术版本、运行环境、证据等级和风险点；
- 至少一个原创价值锚点；
- 证据核验和读者验证的实际计划。

使用 [assets/article-brief.md](assets/article-brief.md) 作为模板。

### 2. 建立证据底座

在写作前整理“主张—证据—边界”表：

- `主张`：文章准备告诉读者什么；
- `类型`：事实、推断、经验或建议；
- `证据`：官方文档、论文、标准、源码、可复现实验或明确标注的工程经验；
- `来源实际说法`：来源能够支持到什么强度；
- `边界`：版本、环境、负载、假设与已知例外；
- `核验状态`：未开始、source-checked 或 peer-reviewed。

没有证据的关键事实不得写成确定语气。代码应尽可能运行或做静态核验；无法验证时明确标注。

核心主张建议加入 `<!-- claim:C01 -->`，并用 [assets/evidence-ledger.json](assets/evidence-ledger.json) 维护。完整方法见 [references/evidence-validation.md](references/evidence-validation.md)。

### 3. 提取风格画像

有参考文章时，只提取可泛化参数：

- 宏观结构：开头如何建立问题、各节如何推进、结尾如何收束；
- 教学机制：先直觉还是先定义，例子、反例、图、代码和小结如何配置；
- 语言节奏：句段长度、主动语态、术语密度、语气和过渡方式；
- 难度曲线：前置知识、概念依赖和每次难度跳跃；
- 搜索结构：标题承诺、问题覆盖、标题层级和内链角色。

输出“保留特征、避免特征、原创替代方案”，然后脱离原文重新设计大纲。详见 [references/style-analysis.md](references/style-analysis.md)。

### 4. 分配认知预算并绘制知识阶梯

先明确：

```yaml
reader_level: absolute_beginner
reading_time_target: "8-12m"
quick_path_minutes: 3
math_budget: intuitive
code_budget: none
core_term_budget: 12
new_terms_per_h2: 2
```

再按依赖组织：

1. 问题与收益：为什么值得学；
2. 全貌：先给完整地图和安全停止点；
3. 直觉模型：形成可用的脑内图景；
4. 精确定义：给直觉补上边界；
5. 最小实践或可观察例子：让读者看到结果；
6. 工作机制：解释系统为何如此运行；
7. 失败模式与权衡：说明何时失效、何时不要用；
8. 生产化与延伸：性能、安全、维护、替代方案和下一步。

若下一节依赖两个以上未解释的核心概念，先插入桥接节或拆篇。每个小节只承担一个主要教学任务。绝对小白长文超过约 10 分钟时，默认提供同页快速阅读路线。

详见 [references/learning-design.md](references/learning-design.md) 和 [references/cognitive-validation.md](references/cognitive-validation.md)。

### 5. 选择结构，而非套统一模板

选择一个主内容类型，并让标题、开头、主体和结尾服务同一种读者需求。不要把教程、参考手册和原理长文无差别混在一起。

具体结构见 [references/content-patterns.md](references/content-patterns.md)。

### 6. 生成可扫读大纲

只看标题层级，也应能复述文章逻辑。大纲必须体现：

- 开头尽早回答“这是什么、解决什么、读完得到什么”；
- 长文有快速路线和完整路线，且不复制内容；
- 每个 H2 对应一个真实问题、决策或学习台阶；
- 每节新增术语和难度跳跃不超过 brief 预算；
- 关键术语在首次使用处解释；
- 示例紧跟其要解释的概念；
- 高风险步骤附近出现验证、回滚或排障说明；
- 结尾给出可执行的决策总结和迁移问题，而不是重复目录。

### 7. 按教学单元写作

默认采用以下微结构，按内容需要删减：

1. `结论或目标`：本节先回答什么；
2. `直觉`：用熟悉概念建立心理模型；
3. `精确定义/机制`：补充必要严谨性；
4. `例子或代码`：产生可观察结果；
5. `反例/边界`：防止过度泛化；
6. `检查点/迁移题`：确认能复述、应用或推出新结论。

语言要求：

- 优先使用主动语态、明确主语和具体动词；
- 一段只完成一个信息动作；复杂长句拆成因果链；
- 缩写首次出现时展开；术语先给简单解释，再给精确定义；
- 类比必须说明映射关系，以及类比在哪些地方失效；
- 公式必须说明用途、符号、普通语言步骤和示例；
- 代码采用“目的 → 环境 → 代码 → 预期输出 → 解释 → 常见失败”的夹心结构；
- 不用空洞开场、重复总结、伪权威语气或无来源的精确数字填充篇幅。

### 8. 增加原创、不可替代的价值

至少选择一个与主题匹配的原创价值锚点：

- 可复现实验或真实输出；
- 源码/协议追踪；
- 原创图、状态机或数据流；
- 条件化决策框架；
- 贯穿 worked example；
- 多个一手来源之间的综合、冲突和边界解释。

不能伪造实验或项目经验。没有一手实践时，可通过透明的来源综合和原创教学模型创造增量。

### 9. 做读者优先的 SEO

SEO 是内容完成后的可发现性设计，不是写作目的。至少产出：

- 一个清晰、独特、准确兑现内容的主标题；
- 2–4 个不同侧重点的备选标题；
- 简短、可读、描述主题的 slug；
- 每页独有、准确概括价值的 meta description；
- 主查询、搜索意图、相关实体与自然同义表达；
- 前置、深入、下一步和证据来源的内链/外链建议；
- 图片或图表建议及描述性 alt 文本；
- 作者、审阅者、发布日期、实质更新日期与方法披露建议。

不要重复堆砌主关键词，不要为每个查询变体复制页面，不要伪造更新时间。没有真实读者测试时，避免“保证看懂、人人都懂、最通俗、彻底掌握”等理解承诺。详见 [references/seo-playbook.md](references/seo-playbook.md)。

### 10. 系列文章：先规划，再逐篇成稿

#### 10.1 `series-plan`：建立系列地图

先创建系列契约和能力依赖图：

- 一个总览/导航页说明读者路径、最终作品和完成标准；
- 每篇只有一个主要学习目标、一个能力增量和一个主要搜索意图；
- 为每篇分配读者等级、时长、术语、数学和代码预算；
- 依赖关系决定学习顺序；需求热度只决定发布优先级；
- 为每篇记录进入状态、继承概念、贯穿案例变更、验证方式和下一篇交接；
- 使用一致的术语表、代码仓库、版本基线、图形语言和证据标准；
- 检查相邻文章是否回答同一问题，必要时合并或重新划界。

使用 [assets/series-map.md](assets/series-map.md)；规划规则见 [references/series-architecture.md](references/series-architecture.md)。

#### 10.2 `series-write`：写总览和完整正文

不要把系列地图或详细大纲称为成稿。先声明交付范围：`overview`、`article:<id>`、`batch:<ids>` 或 `full-series`。用户明确要求“写完整系列”时，默认 `full-series`，并尽量按一篇一个 Markdown 文件交付。

每篇正文必须完成以下动作：

1. 用少量文字恢复上一状态，立即说明当前问题、本篇承诺和完成标志；
2. 围绕一个能力增量推进，不在同篇同时跨越多个知识台阶；
3. 让贯穿案例形成“上一篇结束状态 → 本篇变更 → 本篇结束状态”；
4. 给出可观察验证、失败信号、边界和必要回滚方法；
5. 用“当前能力 → 剩余限制 → 下一篇问题”完成自然交接；
6. 单篇可独立兑现标题，但完整定义、推导和配置由负责页面维护；
7. 维护每篇认知预算、证据状态和读者测试状态；
8. 总览页在子文章完成后再次修订，确保篇次、描述、链接和完成状态与实际成稿一致。

使用 [assets/series-overview-template.md](assets/series-overview-template.md)、[assets/series-article-template.md](assets/series-article-template.md) 和 [assets/series-production-board.md](assets/series-production-board.md)。完整方法见 [references/series-writing.md](references/series-writing.md)。

### 11. 分层验证

完成正文后按顺序执行：

1. **结构与预算**：运行 `article_lint.py --report`；
2. **证据可追踪性**：运行 `evidence_lint.py`；
3. **证据语义**：逐条阅读来源，检查同义支持、范围和强度；
4. **代码/实验**：运行、记录环境和结果，或明确未运行；
5. **编辑自测**：扫读、60 秒复述、迁移题、误解检查；
6. **目标读者测试**：仅在真实执行并有记录时更新状态。

使用 [assets/reader-test-plan.md](assets/reader-test-plan.md)。不得生成虚构试读者或反馈。

### 12. 质量门禁

完成后按 [references/qa-rubric.md](references/qa-rubric.md) 审计。以下任一情况必须返工或阻止发布：

- 标题承诺与正文交付不一致；
- 核心主张无依据，或引用不能语义支持主张；
- 代码、命令或配置无法验证且未说明；
- 难度突然跳跃，依赖概念未解释或未链接；
- 明显超出认知预算，且没有分层或拆篇；
- 只有定义，没有例子、边界、检查点或决策价值；
- 与参考文章出现可识别的表达、案例或叙事复刻；
- SEO 元素诱导点击、关键词堆砌或造成重复内容；
- 自动检查被描述成技术、证据或读者理解的完整验证；
- 声称真实用户测试、同行审阅或实验完成，却没有记录；
- 系列前置形成循环、篇间状态矛盾或把后文知识提前当成已知；
- 多篇重复同一主要搜索意图，或用模板化改写制造近似页面。

## 默认输出顺序

### 单篇模式

除非用户只要正文，否则按以下顺序交付：

1. `写作假设`：最多数条；
2. `内容 brief`：读者、目标、范围、类型、认知预算、搜索意图；
3. `风格画像`：仅在有参考材料时输出；
4. `知识阶梯与术语预算`；
5. `核心主张与证据计划`；
6. `文章大纲`；
7. `完整正文`：Markdown；
8. `SEO 发布包`；
9. `验证范围、证据与待核验项`；
10. `质量评分与修改记录`。

### `series-plan`

交付系列契约、能力依赖图、文章契约表、认知与难度矩阵、贯穿案例增量、搜索意图边界、内链图、证据策略、发布与维护计划。

### `series-write`

默认按独立文件交付：系列总览、各篇完整正文、系列地图、术语表、认知预算台账、连续性台账、证据台账和 SEO 地图。每篇都必须标明文章状态、证据状态和读者测试状态；未完成页面不得用标题或空模板冒充成稿。

用户要求直接成稿时，内部执行规划与审计，只展示成稿、SEO 发布信息和必要的验证范围说明。
