# 系列技术文章写作方法

## 核心定义

系列文章不是把若干相关主题按编号放在一起，而是把一个较大的最终能力拆成多个可独立发现、又能连续学习的页面。

一个合格系列必须同时满足四个条件：

1. **单篇可完成**：读者只打开其中一篇，也能理解页面承诺并得到完整结果。
2. **全系列可累积**：按顺序阅读时，知识、代码或决策能力持续增长，而不是重复入门。
3. **篇间可衔接**：每篇清楚说明继承了什么、新增了什么、把读者带到哪里。
4. **搜索意图可区分**：每篇解决一个独立问题，避免多个页面争夺同一查询。

系列规划使用 `series-plan`；真正撰写总览页和各篇完整正文使用 `series-write`。不要用详细大纲冒充已完成的系列正文。

## 先声明交付范围

在开始前记录 `deliverable_scope`：

- `map`：只交付系列地图和文章契约。
- `overview`：交付系列总览页。
- `article:<id>`：交付指定单篇完整正文。
- `batch:<ids>`：交付指定批次的完整正文。
- `full-series`：交付总览、全部文章和共享资产。

用户说“规划、设计系列”时默认 `map`；用户说“写成系列、完成这个系列”时默认 `full-series`。文章较多时应拆成独立文件，而不是把正文压缩成提纲。

## 1. 锁定系列主轴

写一句系列主张：

> 帮助【目标读者】从【起点状态】到达【最终能力】，通过【贯穿项目或决策场景】逐步掌握【核心知识域】。

同时确定：

- **最终作品**：读者完成后会得到什么，例如一个可运行系统、一份架构决策记录或一套排障方法。
- **主线问题**：贯穿全系列、逐篇逼近的一个大问题。
- **版本基线**：语言、框架、协议、模型、依赖和运行环境。
- **非目标**：本系列明确不覆盖什么。
- **完成标准**：用什么可观察结果证明最终能力已经获得。

没有共同终点的文章合集不应标为系列，可以改成主题索引。

## 2. 给每篇分配“叙事角色”

系列通常从以下角色中选择，不必凑齐所有类型：

| 角色 | 读者问题 | 本篇职责 | 不应承担 |
|---|---|---|---|
| 导航/总览 | 我该从哪里开始？ | 给路径、前置、分支和最终成果 | 讲完所有细节 |
| 定向/基础 | 这个领域的核心对象是什么？ | 建立术语和心理模型 | 堆砌完整参考手册 |
| 首次成功 | 我怎样先做出一个能工作的版本？ | 最小实现与可验证结果 | 过早生产化 |
| 机制深挖 | 为什么会这样运行？ | 解释内部机制和因果链 | 重复完整教程 |
| 能力扩展 | 怎样支持新场景？ | 在既有系统上增加一个能力 | 同时改变多个核心变量 |
| 故障诊断 | 为什么失败，怎样定位？ | 症状、信号、原因、验证和修复 | 只列错误消息 |
| 权衡选型 | 方案 A 还是 B？ | 给决策维度、证据和适用边界 | 宣布绝对赢家 |
| 生产化 | 怎样安全、稳定地上线？ | 性能、安全、可观测性和运维 | 重新解释全部基础 |
| 综合项目 | 我能否独立完成？ | 整合能力并给验收标准 | 引入大量全新概念 |

相邻两篇应该形成“问题—能力—新问题”的自然链条。

## 3. 建立篇间接口

把每篇看作一个有输入和输出的教学模块。写作前填写：

```yaml
article_id: "03"
reader_state_in: "已经运行最小版本，能观察基础输出"
prerequisites: ["01", "02"]
inherited_terms: ["检索器", "候选集合"]
title_promise: "解释并修复召回结果相关性低的问题"
learning_outcome: "能测量召回质量并定位三类常见原因"
new_core_concepts: ["Recall@k", "查询改写", "重排"]
running_example_before: "只有基础向量检索"
running_example_delta: "加入离线评估与重排步骤"
running_example_after: "能生成并比较召回指标"
validation: "在固定测试集上输出指标和错误分类"
non_goals: ["生成质量评估", "在线 A/B 测试"]
next_handoff: "指标改善后仍需处理答案幻觉"
```

约束：

- 一篇只有一个主要能力增量。
- 通常只引入 2–4 个核心新概念；更多时优先拆篇。
- `reader_state_in` 必须能由前置文章的输出得到。
- `validation` 必须可观察，不能只写“理解了”。
- `next_handoff` 应由当前结果自然产生，不制造虚假悬念。

## 4. 先搭全系列骨架，再逐篇成稿

在骨架阶段同步分配每篇的认知预算与验证状态：

- `reader_level`、目标时长、核心新术语预算；
- `math_budget` 与 `code_budget`；
- 是否需要快速阅读路线；
- `evidence_tier`、核心主张和 evidence ledger；
- `reader_test_status`，默认不得超过实际完成的测试范围。

预算不是让所有文章一样长，而是防止某一篇突然承担多个学习台阶。系列读者会累积能力，后文可以提高深度，但必须由前文状态推出。


推荐写作顺序：

1. 写系列契约、依赖图和每篇接口。
2. 建立术语表、版本基线、证据台账和贯穿案例的初始状态。
3. 先写“首次成功”篇，验证系列能产生真实结果。
4. 写基础和机制篇，为首次成功中的必要解释补齐依据。
5. 按依赖顺序写扩展、排障、选型和生产化文章。
6. 写综合项目或终章，验证最终能力是否真的闭环。
7. 回头完成总览页，使导航、描述和链接与实际成稿一致。

总览页可以先有草稿，但应在子文章完成后再次修订。不要让导航页承诺尚不存在的内容而不做状态标记。

## 5. 单篇正文的固定任务

每篇文章使用 [../assets/series-article-template.md](../assets/series-article-template.md)。标题可以灵活，但正文需要完成以下教学动作。

### 5.1 开头：恢复上下文并尽早交付答案

开头应在较短篇幅内回答：

- 这篇解决什么具体问题？
- 读者进入本篇前应已经会什么？
- 本篇相对上一状态新增什么？
- 完成后怎样验证？

推荐结构：

```text
当前状态 → 新遇到的问题 → 本篇承诺 → 可验证产出
```

不要每篇都从行业历史、宏大趋势或相同定义重新开始。系列上下文通常用 1–3 句恢复即可。

### 5.2 主体：围绕一个能力增量推进

先检查本篇预算：若新增术语、公式、代码和抽象程度同时超限，把进阶内容移到可选节、负责页面或下一篇。绝对小白长文提供同页快速路线，避免把快速版和完整版拆成近似 SEO 页面。


默认使用以下循环：

```text
本节结论
→ 必要直觉
→ 精确定义或因果机制
→ 贯穿案例的本次变更
→ 可观察结果
→ 失败模式或边界
→ 检查点
```

一个 H2 只推进一个子问题。示例应紧跟所解释概念，不把所有代码和所有理论分置文章两端。

### 5.3 结尾：固化新状态并交接下一篇

结尾不是逐节复述，而要写清：

- 读者现在能完成什么。
- 贯穿项目现在处于什么状态。
- 哪些限制仍未解决。
- 下一篇为何是自然的下一步。
- 不继续阅读时，读者应该保留哪条决策规则。

用“当前能力—剩余边界—下一步”完成交接。

## 6. 控制重复：让单篇独立，但不反复重写

使用三级回顾策略：

1. **一句恢复**：默认方式，用一句话唤起前文结论。
2. **最小回顾框**：内容关键但读者可能跳读时，用 3–5 个要点恢复。
3. **链接到权威篇**：需要完整推导、定义或配置时，链接到负责该内容的页面。

同一概念再次出现时，必须至少满足一个条件：

- 在新的场景中应用。
- 提升解释深度。
- 暴露先前隐藏的边界。
- 用于新的决策。

否则删除重复内容，改为一句恢复和内链。通常把回顾控制在正文的约 10% 以内；这是编辑提醒，不是机械字数规则。

## 7. 管理贯穿案例和代码状态

每篇记录三种状态：

```text
上一篇结束状态 → 本篇变更 → 本篇结束状态
```

正文或配套台账应说明：

- 本篇修改了哪些文件、组件、配置或决策。
- 为什么只在此时引入这些变化。
- 完整运行命令、依赖和预期输出。
- 对应代码标签、分支或可复制快照。
- 失败时如何恢复到上一篇状态。

任何一篇都不能依赖读者看不到的“未来代码”。若展示最终仓库，必须同时提供与本篇一致的标签或快照。

## 8. 写好篇间过渡

过渡必须传递逻辑，不只是“下一篇见”。可以使用四类连接：

- **能力缺口**：现在能完成 X，但在 Y 条件下会失败，因此下一篇处理 Y。
- **观察异常**：结果已出现，但某个指标或行为无法解释，因此下一篇深入机制。
- **规模变化**：单机或小数据可用，但规模增加后出现新约束，因此下一篇进入生产化。
- **决策分叉**：已经知道可行方案，但不同场景需要选择，因此下一篇比较权衡。

不要故意扣住完成本篇承诺所必需的信息来制造悬念。

## 9. 不同角色文章的写法

### 导航/总览页

使用 [../assets/series-overview-template.md](../assets/series-overview-template.md)。结构：系列价值 → 适合谁/不适合谁 → 最终作品 → 路线图 → 路径分支 → 环境基线 → 文章卡片 → 更新状态。

每张文章卡写清“解决什么、前置什么、完成后得到什么”，不要只列标题。

### 首次成功篇

结构：最小目标 → 环境 → 最少步骤 → 完整代码/配置 → 预期结果 → 验证 → 最常见失败 → 当前限制。

第一次成功必须真实可复现，不用伪代码冒充可运行实现。

### 机制深挖篇

结构：待解释现象 → 心理模型 → 数据流/时序 → 关键算法或实现 → 可观察实验 → 反例与边界 → 回到实践决策。

机制篇必须回答“理解它会改变什么工程决策”。

### 排障篇

结构：症状分组 → 最小诊断信息 → 决策树 → 原因假设 → 验证命令/指标 → 修复 → 预防 → 何时升级处理。

不要把可能原因无序罗列。

### 比较选型篇

结构：决策问题 → 必须满足的约束 → 比较维度 → 同条件证据 → 场景化建议 → 迁移成本 → 不确定项。

必须说明测试条件和不可比较之处。

### 生产化篇

结构：当前原型假设 → 生产威胁模型 → 性能/可靠性/安全/成本 → 可观测信号 → 发布与回滚 → 运维清单 → 剩余风险。

不要只把“加缓存、加监控、做高可用”写成无条件建议。

### 综合项目/终章

结构：任务说明 → 验收标准 → 必要约束 → 实现路径 → 测试 → 失败注入或边界检查 → 结果复盘 → 后续分支。

终章应主要整合已学能力，新增核心概念应尽量少。

## 10. 系列 SEO 与信息架构

采用“总览页覆盖广度、子文章覆盖具体任务”的结构：

- 总览页对应主题级查询和导航意图。
- 子文章对应单一问题、任务、机制或决策意图。
- 标题先写独特承诺，再在末尾标注系列与篇次；不要让所有标题只差编号。
- 每篇有独立的 `primary_query`、slug、meta description 和可验证交付。
- 同一查询、同一读者状态、同一交付的页面应合并。
- 版本文章需要清楚标版本、迁移关系和 canonical 策略。
- 内链锚文本说明目标页能解决什么，不使用“上一篇”“点这里”作为唯一语义。

编号帮助学习导航，但不能替代页面本身的语义标题。

## 11. 连续性台账

连续性不只包括术语和代码，还包括：

- 认知预算：相邻篇的读者等级、时长、术语、数学和代码深度；
- 证据状态：核心主张负责页面、来源版本、语义核验和冲突结论；
- 理解验证：自测、真实试读、暴露的误解和复测结果。

不得生成虚构试读者、完成率或反馈。没有真实测试时保持 `not_run` 或 `self_check_only`。


使用 [../assets/series-production-board.md](../assets/series-production-board.md) 维护：

- 文章状态和依赖。
- 术语的首次定义与规范写法。
- 贯穿项目每篇结束时的状态。
- 主张、证据、版本和适用边界。
- 每页搜索意图与内容重叠。
- 图、代码、数据和截图的复用位置。

改动上游文章时，必须沿依赖图检查下游，而不是只修当前页面。

## 12. 系列级质量门禁

出现以下任一问题，系列状态为 `REVISE` 或 `BLOCKED`：

- 某篇无法独立兑现标题承诺。
- 前置依赖不存在、形成循环，或后文知识被提前当成已知。
- 同一术语在不同篇含义冲突，却没有明确说明语境。
- 贯穿案例的环境、代码或数据在篇间无解释地变化。
- 多篇覆盖同一主要搜索意图，仅替换标题或例子。
- 总览页描述、篇次、链接或完成状态与实际文件不一致。
- 最终文章没有验证系列声明的最终能力。
- 系列中大量段落、开头或总结只是模板化重复。
- 某篇明显超过认知预算，且没有快速路线、进阶分层或拆篇说明。
- 核心主张只有链接完整性检查，没有完成来源语义核验，却标为 verified/reviewed。
- `reader_test_status` 声称已通过，但没有真实试读记录。

完成后先逐篇运行：

```bash
python scripts/article_lint.py path/to/article.md --report
python scripts/evidence_lint.py path/to/evidence-ledger.json --article path/to/article.md
```

再运行：

```bash
python scripts/series_lint.py path/to/series
python scripts/series_lint.py path/to/series --json
```

脚本只检查可自动发现的结构、预算、台账、依赖和重复风险，不能替代技术审阅、来源语义核验或真实读者测试。

## 13. `series-write` 默认交付结构

除非用户指定其他格式，按独立文件交付：

```text
series-output/
├── 00-series-overview.md
├── 01-<semantic-slug>.md
├── 02-<semantic-slug>.md
├── ...
├── series-map.md
├── glossary.md
├── continuity-ledger.md
├── evidence-ledger.json
├── reader-test-report.md
└── seo-map.md
```

每篇完整正文都应附有：文章契约、可验证结果、上一篇/下一篇和必要来源。未写完的页面必须明确标为计划中，不能用标题或空模板冒充成稿。
