# 技术文章的学习设计

## 读者差距

把文章内容视为：

```text
读者完成目标所需的知识与技能 − 读者当前已有的知识与技能
```

先写读者等级、已有知识和常见误解，再列目标任务。不要把作者知道的一切都写进去，只补齐完成目标所需的差距。

读者等级、阅读时长、术语、数学和代码预算详见 [cognitive-validation.md](cognitive-validation.md)。

## 知识依赖图

为每个核心概念记录：

- 前置概念；
- 读者需要达到的掌握层级：认识、解释、应用、诊断、权衡或设计；
- 最小可观察证据：输出、图、测试、日志、指标或决策；
- 常见错误模型；
- 是否计入核心新术语预算。

按拓扑顺序组织文章。若某节依赖两个以上尚未解释的核心概念，插入桥接内容或拆分为独立文章。

## 七级知识阶梯

| 层级 | 读者问题 | 合适内容 |
|---|---|---|
| 0 场景 | 为什么我要关心？ | 问题、代价、使用场景、非目标 |
| 1 直觉 | 我先怎么想它？ | 心理模型、图、简单类比 |
| 2 定义 | 它准确是什么？ | 术语、边界、不是什么 |
| 3 最小实践 | 我怎样看到它工作？ | 可运行例子、预期输出、验证 |
| 4 机制 | 为什么会这样？ | 数据流、控制流、算法、协议 |
| 5 权衡 | 何时失效或不该用？ | 反例、故障、性能、安全、替代 |
| 6 生产化 | 怎样在真实系统中使用？ | 监控、容量、演进、治理、迁移 |

单篇文章不必覆盖全部层级，但不得跨过完成目标所需的中间层。系列文章可把层级拆到不同篇。

## 先分配认知预算

在大纲前明确：

```yaml
reader_level: absolute_beginner
reading_time_target: "8-12m"
math_budget: intuitive
code_budget: none
core_term_budget: 12
new_terms_per_h2: 2
quick_path_minutes: 3
```

这些是编辑约束，不是硬性的通用规则。超出时说明原因，并选择删除、桥接、分层或拆篇，而不是默认继续加内容。

小白长文使用渐进披露：先给答案和全貌，再进入机制，把公式、源码和性能放到可选进阶层。快速路线应指向同一页面的关键章节，不创建内容近似的 SEO 页面。

## 教学单元

一个完整的小节通常包含：

1. **本节答案**：一句话说明要点。
2. **直觉模型**：把新知识接到读者已知概念上。
3. **严谨解释**：定义、机制或条件。
4. **可观察例子**：代码、图、表、日志或场景。
5. **边界/反例**：指出模型何时失效。
6. **检查点**：让读者用一句话或一个小任务确认理解。

不要机械重复六项；只保留对当前概念有帮助的部分。单个 H2 只推进一个主要因果链或任务。

## 术语解释卡

首次出现的核心术语尽量回答：

```text
简单解释：用普通语言说它解决什么。
精确定义：给出必要的技术边界。
作用位置：它在系统或流程中的哪一层。
例子：一个具体实例。
非例子：容易混淆但不属于它的情况。
后续依赖：后文为什么还需要记住它。
```

缩写首次出现时写全称。不要在一句话或同一段里连续引入多个新术语。核心新术语应列入 brief 和 frontmatter，便于检查预算。

## 类比规则

类比是脚手架，不是证明。每个类比包含：

- 已知对象与未知对象的对应关系；
- 类比帮助理解的具体部分；
- 类比失效的边界；
- 随后回到真实机制。

避免用另一个更陌生的技术概念解释当前概念。目标读者若记住类比却说错真实机制，类比就需要重写。

## 公式解释

公式必须形成闭环：

1. 公式回答什么问题；
2. 每个符号代表什么；
3. 用普通语言逐步翻译计算；
4. 给一个小输入和可观察输出；
5. 说明公式省略了哪些真实细节。

`math_budget: none` 时，公式不能承担主路径；`intuitive` 时，只保留帮助精确定义的少量公式。

## 代码夹心

代码块前后必须形成闭环：

1. 目的与环境；
2. 最小、完整、可复制的代码；
3. 预期输出或验证命令；
4. 对关键行的解释，而非逐字朗读；
5. 常见错误、版本差异与回滚方式。

长代码优先放仓库，正文只保留与当前教学目标直接相关的片段。`absolute_beginner + code_budget:none` 时，不用代码替代核心解释。

## 图表选择

- 关系与依赖：架构图或概念图；
- 时间与顺序：时序图；
- 状态变化：状态机；
- 数据流转：数据流图；
- 多方案权衡：表格或决策矩阵；
- 性能变化：带环境说明的图表。

图必须在正文中被解释；alt 文本描述图传达的信息，而不是只写“架构图”。

## 语言与认知负担

- 主动语态优先，明确谁执行了什么动作；
- 一个段落只承担一个信息动作；
- 长因果链拆成步骤或图，不用多层从句隐藏逻辑；
- 先用常用词，再给专业词；不要为了“显得专业”增加术语；
- 重要限制放在相关步骤附近，不统一堆到文末；
- 每个主要章节结束时，用一句可复述结论或一个微型练习收束；
- 一节若同时提升术语、抽象、数学和实现复杂度，优先拆分。

## 理解度测试

### 扫读测试

只读标题、首句、图注和代码输出，能否知道文章的完整路径？

### 复述测试

目标读者能否不用原文回答：

- 它是什么？
- 为什么有用？
- 如何使用或验证？
- 何时不适用？
- 下一步应学什么？

### 迁移测试

读者能否回答正文未直接给出、但可由机制推出的问题？只能复读原句不算形成理解。

### 中断恢复测试

读者从任一 H2 开始，能否通过前置链接或一句背景说明恢复上下文？

### 失败前置测试

读者会在哪一步最可能失败？文章是否在失败发生前提供了信号、诊断和恢复路径？

### 验证范围

自动结构检查、作者自测和真实目标读者测试必须分开记录。使用 [../assets/reader-test-plan.md](../assets/reader-test-plan.md)，并遵循 [cognitive-validation.md](cognitive-validation.md) 中的状态定义。未运行真实测试时，只能声称“面向目标读者设计”，不能声称“目标读者已经验证能看懂”。
