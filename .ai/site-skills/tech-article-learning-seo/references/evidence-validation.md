# 主张—证据语义核验

## 目的

引用存在不等于引用支持结论。证据核验要确认：来源究竟说了什么、适用范围是否一致、文章措辞是否比证据更强，以及反例或版本差异是否被隐藏。

自动脚本只能检查引用完整性、台账字段和主张标记的可追踪性。语义支持关系必须由写作者或审阅者实际阅读来源后判断。

## 证据等级

```yaml
evidence_tier: light | standard | rigorous
```

- `light`：稳定、低争议的背景解释；仍不能编造事实或来源。
- `standard`：技术原理、工程指南、产品能力和一般发布文章。核心事实需要一手来源或可复现实验。
- `rigorous`：医疗、法律、金融、安全、高争议判断、性能基准、重大采购/架构决策。要求完整台账、范围核验和独立审阅或明确披露未完成项。

## 区分主张类型

| 类型 | 说明 | 需要什么 |
|---|---|---|
| `fact` | 可由外部事实判断真伪 | 来源、定位、版本/条件、支持强度 |
| `inference` | 从多个事实推出的解释 | 支持事实、推理链和不确定性 |
| `experience` | 实际项目、测试或观察 | 真实来源、环境、方法、原始结果和可泛化边界 |
| `recommendation` | 对行动或选型的建议 | 决策目标、约束、权衡依据和替代方案 |

不要把推断、经验或建议伪装成无条件事实。

## 五步语义匹配

对每个核心主张执行：

1. **同义支持**：来源是否真正表达了同一结论，而不是只出现相同关键词？
2. **范围一致**：版本、模型、数据集、人群、环境、时间和负载是否一致？
3. **强度一致**：来源说“可能/在实验中/相关”，正文是否错误升级为“必然/普遍/因果”？
4. **来源层级**：能否追溯到官方文档、标准、论文、源码、数据或原始实验？
5. **反证与例外**：是否存在会改变结论的重要反例、冲突来源或已知限制？

记录审阅结论：

- `direct`：来源直接支持正文措辞；
- `partial`：只能支持有限范围，正文必须带限定；
- `unsupported`：来源未支持该结论；
- `contradicted`：来源与正文相反；
- `unclear`：证据不足或无法判断。

核心主张为 `unsupported`、`contradicted` 或 `unclear` 时不得写成确定结论。

## 主张台账

使用 [../assets/evidence-ledger.json](../assets/evidence-ledger.json)。每条核心主张至少记录：

```json
{
  "id": "C01",
  "importance": "core",
  "claim_type": "fact",
  "published_claim": "文章中实际使用的完整措辞",
  "article_location": "## 对应章节",
  "source_type": "paper",
  "source": "来源标题或稳定标识",
  "source_locator": "章节、页码、段落、代码行、实验记录或 URL",
  "source_summary": "来源实际支持的内容",
  "reviewer_verdict": "direct",
  "scope_match": "yes",
  "strength_match": "yes",
  "qualifier_in_article": "",
  "limitations": "",
  "verification_status": "source_checked"
}
```

建议在正文核心主张附近加入不可见标记：

```markdown
Transformer 使用自注意力在序列位置之间汇总信息。[2]
<!-- claim:C01 -->
```

这样可以把正文、引用和台账绑定。标记不是 SEO 技巧，不影响读者显示；它只服务编辑追踪和后续更新。

## 来源优先级

优先顺序不是绝对，但核心主张应尽量靠近原始证据：

1. 标准、法律文本、官方规范；
2. 原始论文、官方技术报告、源码、提交记录；
3. 官方产品文档与变更日志；
4. 可复现实验、公开数据和完整方法；
5. 可信工程复盘或专家分析；
6. 二手教程、聚合文章和社交讨论。

二手来源可用于发现线索或补充实践背景，不应冒充原始证据。来源有利益关系时披露。

## 代码、性能和实验主张

### 代码

记录：

- 版本与依赖；
- 运行环境；
- 命令；
- 预期输出；
- 实际验证状态；
- 未验证原因。

不能运行时写“示例代码/未经运行验证”，不要写“可直接运行”。

### 性能

性能结论必须同时给：

- 硬件、软件版本和配置；
- 数据规模、请求分布、并发与预热；
- 指标定义和统计方法；
- 基线和误差；
- 可复现材料；
- 不能外推到哪些环境。

“快 3 倍”若缺少环境和基线，属于不完整主张。

### 图表和数据

注明来源、单位、时间、采样方式和不确定性。截取图表时不要隐藏会改变解释的坐标、基线或异常点。

## 工作流

1. 写大纲时列出 5–15 个会改变读者判断的核心主张。
2. 在写正文前找到来源并记录来源实际说法。
3. 写正文时使用与证据强度一致的措辞，并加入 `claim` 标记。
4. 完稿后逐条做范围和强度匹配，不只检查链接能否打开。
5. 对冲突证据写出差异原因或保留不确定性。
6. 运行：

```bash
python scripts/evidence_lint.py evidence-ledger.json --article article.md
```

7. 输出验证范围：哪些已 source-checked、哪些只是编辑自检、哪些仍未核验。

## 自动检查边界

`evidence_lint.py` 可以发现：

- 核心主张缺少来源或定位；
- 主张 ID 重复；
- 正文标记与台账不一致；
- 标为部分支持却没有限定；
- 标为同行审阅却没有审阅者；
- 引用标记没有出现在主张附近；
- 明确记录为不支持或矛盾的核心主张。

它不能判断论文是否可靠、来源是否被误读、实验是否造假或两个句子是否真正语义等价。最终语义结论必须由实际阅读和审阅产生。
