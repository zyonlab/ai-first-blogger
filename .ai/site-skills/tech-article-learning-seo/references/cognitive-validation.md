# 认知预算与理解度验证

## 目的

“结构清楚”不等于“目标读者已经理解”。认知预算用于限制一次需要处理的新信息；理解度验证用于区分作者自检、自动检查和真实读者测试。

本文件适用于小白入门文、复杂原理解释、长教程和系列文章。数值是默认编辑预算，不是普适定律，也不是 SEO 排名公式。主题、语言、读者和发布场景不同时可以调整，但必须说明理由。

## 读者等级

先选择一个主要等级，不要只写“面向所有人”。

| `reader_level` | 默认已有知识 | 写作要求 |
|---|---|---|
| `absolute_beginner` | 只使用过相关产品，不假设数学、代码或专业背景 | 普通语言先行；每次只推进一个因果链；术语、公式和代码都要给进入台阶 |
| `beginner_engineer` | 能读基础代码，理解常见软件概念，但不熟悉当前主题 | 可使用最小代码和轻量抽象；关键机制仍需示例、输出和边界 |
| `intermediate` | 已完成基础实践，能阅读文档和简单论文/源码 | 聚焦机制、诊断、权衡和实现细节；明确省略的基础链接 |
| `expert` | 熟悉领域术语、实现和常见权衡 | 优先证据、差异、边界和新洞见；仍需声明版本、假设与结论强度 |

出现“小白、零基础、不懂编程、通俗入门”等要求时，默认使用 `absolute_beginner`。出现“工程师入门”时，默认使用 `beginner_engineer`。不要因为主题技术性强就擅自提高读者等级。

## 认知预算契约

写作前记录：

```yaml
cognitive_budget:
  reader_level: absolute_beginner
  reading_time_target: "8-12m"
  quick_path_minutes: 3
  math_budget: intuitive
  code_budget: none
  core_term_budget: 12
  new_terms_per_h2: 2
  abstraction_jumps_per_section: 1
  example_density: "每 1-2 个核心概念至少一个可观察例子"
  detail_strategy: progressive-disclosure
```

### 阅读时长预算

按读者完成目标需要的最短路径确定，不为满足字数而扩写。

| 目标时长 | 建议用途 | 核心新术语默认预算 |
|---|---|---:|
| 3–5 分钟 | 快速建立全貌或回答单一问题 | 5–8 |
| 8–12 分钟 | 完整入门解释 | 8–12 |
| 15–25 分钟 | 带实践或机制的系统入门 | 12–20 |
| 25 分钟以上 | 深度文章、教程或专题 | 不设统一上限，但应提供阅读路线、术语表或拆篇判断 |

当 `absolute_beginner` 文章预计超过 10 分钟时，默认增加“快速阅读路线”：告诉读者只读哪些段落就能获得全貌。快速路线应使用同一页面的锚点，不复制一篇近似短文。

### 术语预算

核心新术语是读者必须记住、后文会继续依赖的概念，不包括普通名词和只出现一次的背景词。

- `absolute_beginner`：单个 H2 默认不超过 2 个核心新术语。
- `beginner_engineer`：单个 H2 默认不超过 3 个。
- 超出预算时，优先删除非目标内容、增加桥接例子或拆节，而不是只加括号解释。
- 首次出现时给普通语言解释；需要严谨性时再补精确定义。
- 同一段不要连续定义多个缩写。

建立最小术语台账：

| 术语 | 读者已知连接点 | 简单解释 | 精确定义 | 首次出现 | 后续依赖 |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

### 数学预算

| `math_budget` | 允许内容 |
|---|---|
| `none` | 不依赖公式完成理解；必要符号放到可选附录 |
| `intuitive` | 最多使用少量公式作为精确定义；逐个解释符号并翻译成普通语言步骤 |
| `light` | 可使用基础代数、概率或复杂度；推导只保留完成目标所需步骤 |
| `formal` | 可给完整推导，但仍说明假设、符号和结论用途 |

公式出现前先说明它回答什么问题，公式后必须给普通语言解释和一个可观察例子。公式不能替代因果说明。

### 代码预算

| `code_budget` | 适用方式 |
|---|---|
| `none` | 使用流程图、表格、伪输入输出或生活化例子 |
| `pseudocode` | 只展示控制流或数据流，不要求环境 |
| `minimal` | 单个最小可运行片段，包含环境与预期输出 |
| `production` | 可展示多文件或工程配置，但提供仓库、版本和回滚点 |

读者没有编程基础时，不要用代码承担核心解释；代码只能作为可选验证。

## 难度跳跃控制

每节最多提升一个主要维度：

- 新术语数量；
- 抽象程度；
- 数学形式化；
- 实现复杂度；
- 决策不确定性。

若同一节同时引入三个新术语、一个公式和一段代码，应拆成：直觉 → 术语 → 示例 → 可选机制。若下一节依赖两个以上尚未解释的核心概念，插入桥接节或拆篇。

## 渐进披露

长文默认分四层：

1. **答案层**：开头直接回答主要问题。
2. **全貌层**：一张流程、图或六句话建立地图。
3. **机制层**：按依赖解释组成和因果关系。
4. **深入层**：公式、源码、性能和争议放在明确标注的进阶节或链接中。

不同层回答不同深度，不重复改写同一段。读者应能在完成答案层或全貌层后安全停止。

## 理解度验证等级

使用明确状态，避免把自动检查写成用户验证：

| `reader_test_status` | 含义 | 可以声称什么 |
|---|---|---|
| `not_run` | 未做理解度测试 | “面向该读者设计” |
| `self_check_only` | 作者/模型完成扫读、复述题和依赖自检 | “已完成编辑自检” |
| `pilot_run` | 至少一名目标读者完成测试并记录观察 | “完成小规模试读”，不得泛化 |
| `target_reader_passed` | 按预设验收标准完成目标读者测试 | 可准确描述测试范围和结果 |
| `needs_revision` | 测试暴露关键误解或任务失败 | 不应发布为已验证版本 |

自动 linter 只能证明“未发现它能识别的形式风险”。它不能证明技术正确、引用支持结论或读者理解。

## 读者测试协议

先写验收标准，再观察，不要在看到结果后临时降低标准。

### 任务 1：60 秒复述

读者不看原文回答：

- 它是什么？
- 为什么有用？
- 完整流程包含哪些关键步骤？
- 最大边界是什么？

记录遗漏和错误模型，不只记录“感觉懂了”。

### 任务 2：解释给别人听

让读者用自己的例子解释一个核心机制。若只能复读原句，说明尚未形成可迁移的心理模型。

### 任务 3：迁移问题

提供正文没有直接出现、但能由机制推出的小问题。目标是验证理解，不是记忆。

### 任务 4：误解检查

针对 brief 中列出的常见误解设置判断题或情景题，并要求说明原因。

### 任务 5：定位与行动

对于教程或操作文，让读者实际完成一步、找到一个错误信号或做出一个条件化选择。

### 记录维度

- 完成时间与中断位置；
- 是否需要提示；
- 核心误解；
- 无法解释的术语；
- 任务是否完成；
- 自信度与实际正确率是否一致；
- 建议删除、桥接或移动的内容。

使用 [../assets/reader-test-plan.md](../assets/reader-test-plan.md) 记录。不得编造参与者、反馈、完成率或“用户都看懂了”等结论。

## 发布措辞

未做目标读者测试时，使用：

- “面向零基础读者设计”；
- “不要求数学或编程前置”；
- “按直觉到机制的顺序解释”。

避免：

- “保证看懂”；
- “人人都能懂”；
- “最通俗”；
- “看完彻底掌握”；
- “小白一看就会”。

这些词既难验证，也容易让标题承诺超过正文交付。
