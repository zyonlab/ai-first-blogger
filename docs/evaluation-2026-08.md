# 评估报告：用 shumer.dev 仿站全面测试

被测对象：`examples/indie-ai-builder`——一个模仿 [shumer.dev](https://shumer.dev/) 的
示例站（虚构人物 kai lund，5 篇中文文章，等宽极简模板）。

选它做压力测试的理由是它**和框架的默认审美相反**：框架出厂是圆角卡片 + 网格 + 标签胶囊，
参考站是零圆角、零边框、单列、纯文本。一个模板层如果只能改颜色，这个站就做不出来。

测试内容：走完整管道（build → validate → analyze → metrics → 自测 → 回归 → Lighthouse），
把渲染结果和参考站逐项比对，然后**用产品目标去解释每一处差距，能修的当场修**。

---

## 0. 结论速览

| 维度 | 结论 |
|---|---|
| 模板 | token 层不足以仿站，覆盖层可以；但覆盖层上线时**有一半是坏的**（见 2.2） |
| SEO | 闸门 29/29 全绿，Lighthouse 全站 100/100/100——**但两条缺陷是 Lighthouse 抓的，不是闸门** |
| 文章风格 | 打分 5/5 满分；同时**违反了 voice.md 正文写明的篇幅约定**，管道全程无感 |
| 产品设计 vs 目标 | 三平面成立；最大缺口是**「AI 优先」那一半没进脚手架** |
| 架构合理性（技术项） | 注册表 + 派生 + 单向依赖成立；**同一个失败模式已出现五次** |
| 与用户规划文件的耦合（产品项） | 意图层耦合度低（好）；**agent 操作契约耦合度为零——因为它根本没发出去**（坏） |

本轮测试共发现并修复 **4 个产品缺陷**，新增 **2 条闸门规则**（C-28、C-29）和
**3 个回归场景**。评估之后又做了一轮优化（§8b），把「本轮不修」的四项全部做掉。

合计：闸门 27 → **29 条**，回归 13 → **19 个场景**，版本 **0.2.0**。

pnpm build            22 页 + _redirects(1) + _headers + sitemap
pnpm validate         29/29 规则，0 error 0 warning

的判断，只有浏览器算数。

## 2. 模板

### 2.1 token 层做到哪、做不到哪

`site/themes/mono.css` 声明 54 个 token，把字体栈、颜色、行高、正文宽度全部对齐了参考站
（`ui-monospace…`、`#111111`、`--content-width: 760px`、`--prose-leading: 1.75`）。

然后渲染出来的页面**和参考站毫无相似之处**。量化对比（改造前，`dist/writing/index.html`）：

| | 本站 | shumer.dev |
|---|---|---|
| 列表布局 | 2 列 `.grid` | 单列 |
| 条目容器 | `<article class="card">` ×5 | 无容器，纯行 |
| 标签 | 6 个胶囊 | 无 |
| 圆角 | `999px / 24px / 10px` | 0 |
| 边框 | 30 条 `border: 1px` | 0 |
| 页头 | 圆角胶囊导航条 | 一行文字 |

原因扫一遍 `global.css` 就清楚了：

| 属性 | 出现次数 | 走 `var()` 的 |
|---|---|---|
| `box-shadow` | 13 | **13** |
| `padding` | 37 | 7 |
| `margin` | 35 | 6 |
| `gap` | 28 | 6 |
| `font-size` | 43 | 1 |
| `border-radius` | 37 | **0** |

**token 层覆盖了颜色和阴影，没覆盖形状和字号阶。** 一个连 `--radius` 都不存在的主题系统，
能换配色，换不了气质。这不是 bug，是层的边界——但边界必须说清楚，否则用户会花两小时
调 token 然后发现方向就是错的。

### 2.2 覆盖层：能做到，但上线时是坏的

`site/templates/` 是 WordPress/Ghost 子主题那套。这个站最终用了 3 个覆盖文件、301 行：

```
site/templates/pages/index.astro          整页替换首页（单列 + 分隔线分段）
site/templates/pages/[type]/index.astro   列表页改单列、去标签云
site/templates/components/Header.astro    扁平文字页头
site/templates/cards/ArticleCard.astro    卡片 → 平铺行
```

改完之后：`.card` 0 个、`.grid` 0 个、`site-header` 消失，页面和参考站在结构上一致。

**但 `components/` 这一路原本是不生效的。** 写好 `Header.astro`，构建成功，日志照常打印
`2 overridden`，`dist/` 里渲染的还是引擎的圆角导航。原因：

> 覆盖用 `enforce: 'pre'` 的 Vite 插件匹配 `@components/…`，前提是 `pre` 排在 alias 之前。
> **不是。** Vite 的 `resolve.alias` 排在所有用户插件之前，`pre` 也不例外。插件永远看不到
> 这个 id，因为它早就被替换成包内的绝对路径了。

而日志里的 `2 overridden` 是**页面覆盖**的计数——它走 `injectRoute`，另一条路，一直是好的。
所以现象是：日志说覆盖成功，页面没变，没有任何报错。

修法（`packages/engine/integration.ts`）：重定向挂到 alias 条目自己的 `customResolver` 上，
另留一个 pre 插件处理引擎内部的相对同级导入（`./ThemeToggle.astro`）——这两条路径都要覆盖，
而且覆盖文件用相对路径导入同级时必须拿到**引擎的**那份，否则自己导入自己。

新增 3 个回归场景钉死：组件覆盖到达页面、页面覆盖到达 URL、**丢了 head 的覆盖被闸门拦住**。
最后一条是这个层敢交给用户的全部理由——实测覆盖一个跳过 `BaseLayout` 的页面，
C-01/C-07/C-16 三条同时报错，构建阻断。**随便改，但改坏了发不出去。**

### 2.3 覆盖粒度偏粗

为了把列表从两列改成一列，`[type]/index.astro` 覆盖文件 68 行里有 **44 行和引擎逐字相同**
——`getStaticPaths`、三段 JSON-LD、面包屑，全部照抄，只为改一个 class 名。

我一开始把根因判断成「列表布局住在机制层，`site/` 无处表达」。**这个判断是错的**，
后来实测推翻了：registry 是 `{ ...engineType, ...siteType }`，而 `site/content-types.yaml`
是整份 spread 进去的，所以 `listLayout` 一直是通的——只是没文档、没校验、也没有第三个取值。

```yaml
posts:
  listLayout: stack     # → dist/writing/index.html: class="section stack"
  listTagCloud: false
```

**已修**：`stack` 进枚举并加 `.stack` 样式，取值非法时按名字报错（`masonry` → 列出合法值），
两条回归场景。示例站那 68 行覆盖**整个删掉**，换成两行 YAML，渲染完全一致。

真正的粒度问题还在（覆盖页面仍要照抄 plumbing），但真实样本从 1 个变成 0 个——
**在找到第二个真实案例之前不该为它设计 slot 机制**。`docs/specs/templates.md` 现在开头
就写着：只改一个值就不要覆盖页面，那是一份会腐烂的复制。

## 3. SEO

### 3.1 闸门与 Lighthouse 的分工，以及分工的漏洞

闸门 29/29 全绿、0 error 0 warning。Lighthouse 跑完 **22 页里 21 页 SEO 失败**（0.92 < 0.95）。

两条缺陷，闸门一条都没看到：

**（1）没有 href 的锚点，出现在每一页。**

`Footer.astro` 写死了四个社交平台：

```astro
<a href={site.social.youtube}>YouTube</a>
```

这个站只配了 github 和 x。Astro 遇到 `undefined` 的属性会**整个丢掉**，于是产物里是
`<a>YouTube</a>`——看起来像链接、键盘到不了、爬虫跟不了。`crawlable-anchors` 得 0 分。

这同时是个分层错误：**「我在哪些平台上」是意图**，`site.social` 本来就是开放 map，
`sameAs` 也一直是 `Object.values(site.social)` 直接读的。只有这个组件坚持要提前知道平台名字，
结果是用 Mastodon 的站没地方写，四个都不用的站白得一身坏 markup。

修法：从 `site.social` 派生，空值不渲染。新增 **C-28 每个锚点可跟随**（缺失/空/`javascript:`
的 href 全部 error，`#fragment` 放行——跳转链接依赖它）。

**（2）`h1 → h3`，五种页面类型全中。**

```
/topics/  h1 h3 h3 h3 h3 h3
/uses/    h1 h3 h3 h3
/writing/ h1 h3 h3 h3 h3 h3
```

卡片标题写死 `<h3>`。首页上卡片在 section 的 `<h2>` 底下，h3 是对的；列表页上卡片直接在
页面 `<h1>` 底下，h3 就跳了一级。**这正是 C-09 存在的意义**——它只是从来没被指向引擎自己的
markup，只查文章正文的 Markdown。

修法：卡片接受 `headingLevel` 属性（默认 3，首页不变），列表页传 2；`uses` / `work-with-me`
的条目直接升到 h2。新增 **C-29 渲染后的标题层级**，查 `dist/`。

### 3.2 修完的结果

```
22 页 Lighthouse            SEO 100 · Accessibility 100 · Best Practices 100
闸门                        29/29，0 error 0 warning
```

（`/404.html` 的 SEO 分按配置豁免——一个 noindex 的错误页拿 SEO 分没有意义。）

### 3.3 这一节真正的结论

不是「SEO 满分」，是：**闸门有 27 条规则、Lighthouse 是不阻断的旁路 job，而这次两条缺陷
全在旁路里被抓到。** 旁路抓到的东西必须回流成闸门规则，否则「不阻断」就等于「没人看」。
这次回流了两条。

值得记一笔的是产品判断没变：Lighthouse 依然**不进阻断路径**。它要 Chrome、跑 4 分钟，
闸门跑 1 秒。正确的关系是 Lighthouse 负责发现新类别，闸门负责让同一个类别不再发生。

## 4. 文章风格

### 4.1 打分层

5 篇全部 100 分，28 处门面文案 0 命中。这个分数**是站点自己的信号表算出来的**，不是通用规则：
`site/voice.md` 的 frontmatter 声明了 6 组 avoid（AI 布道腔、三段式、优缺点对仗……）和
3 组 expect（第一手经验、边界与代价、具体数字），全部由这个站定义。

已验证不是硬编码：同一篇布道腔文章，示例站 voice 得 0 分，骨架 voice 得 60 分，
40 分差额全部来自站点声明。

### 4.2 打分层管不到的那一半

`site/voice.md` 正文写着：

> 一千五到两千字，六到十个小标题，几乎不用列表

实际产出：

| 文章 | 正文字数（去代码） | 小标题 |
|---|---|---|
| cutting-the-eval-set | 977 | 6 |
| retries-made-it-worse | 939 | 6 |
| timeout-is-not-free | 995 | 6 |
| what-i-actually-changed… | 1084 | 6 |
| what-i-stopped-doing-alone | 1326 | 8 |

**五篇全部低于站点自己写下的下限**，最短的不到六成。而管道给了 100 分、0 error。

原因是设计上就这样，文档也承认：frontmatter 给 `analyze` 读，正文给写作的 agent 读。
唯一的长度闸门是 C-26 的 `minBodyWidth: 400`（约 200 汉字），注释明说「用来抓残桩，不是用来
管长度」。

但后果值得正视：**voice.md 里凡是写成散文的约定，对管道等于不存在，而 agent 会在它们上面
飘。** 这不是「voice.md 写得不好」，是产品在 signals（可判定）和正文（不可判定）之间
留了一条缝，缝里恰好装着篇幅、结构、小标题写法这些**其实可判定**的东西。

**已修**：`voice.md` 的 `thresholds` 新增 `minBodyWidth` / `minHeadings` / `maxHeadings` /
`maxListRatio`，和已有的 `codeRatio`、`openerWidth` 是同一个形状。约定和计分从此是同一份文件。

**默认全部惰性**（`null`）——一个出厂就生效的新计分维度，等于悄悄改写每个既有站点的历史
分数；而一份没声明长度的 voice，就是没同意过任何长度。

示例站声明之后立刻打脸：五篇全部命中，分数 100 → 90，命中的正是它正文里写着的那条。
文章已补齐（§8b）。

### 4.3 风格闸门的默认值是对的

`policy.style.minScore: null`——默认不阻断。理由写在 policy 里：分数指出机械痕迹，
判断不了好坏，要先拿自己已发布的文章校准。这个克制是对的，C-06 的历史（描述长度下限
被迫下调两次，因为一直误伤好的短句）就是反面教材。

## 5. 产品设计 vs 目标（产品项）

目标：**AI 友好的静态博客生成器**——用户自定义站点规划 / 模板 / 分类 / 写作风格，
管道做 SEO 校验（影响发布）和 deslop。

| 目标 | 兑现情况 |
|---|---|
| 自定义站点规划 | ✅ `site/*.yaml` 五个文件；pillar 无 topic 认领直接构建失败 |
| 自定义分类 | ✅ taxonomy 三合一，category 从 topic 派生 |
| 自定义写作风格 | ✅ 篇幅 / 小标题 / 列表占比已可声明（§8b）；语感仍归散文，这是对的分工 |
| 自定义模板 | 🟡 三层齐了（token / 意图值 / 覆盖）；token 层仍不覆盖形状（2.1），有意不做 |
| SEO 校验影响发布 | ✅ 29 条规则，error 即 exit 1，CI 门控部署 |
| deslop | ✅ 文章 + 门面文案两类；后者出现在更多页面上，这个扩展是对的 |
| 规划前置检查 | ✅ 七领域，没规划好一条内容规则都不跑 |

### 5.1 最大的缺口：「AI 优先」那一半没发出去

这是本轮最重的产品发现。实际跑一遍脚手架：

```bash
npm create aifb@latest my-blog --example indie-ai-builder
```

产出的目录：

```
site/  content/  src/  public/  .github/  astro.config.mjs  package.json
```

**没有 `.ai/skills/`，没有 `prompts/`，没有 `AGENTS.md`，没有 `docs/`。**

也就是说，`create-aifb` 交付的是「机制 + 意图骨架」，不包含**agent 的操作契约**：
边界在哪、先跑 `pnpm context` 再读配置、五个任务对应五个 prompt、六条护栏
（不改 DNS、不提交密钥、不手写派生表面、**不为让构建通过而消音规则**）。

后果具体而不抽象：新站的 `package.json` 里有 `pnpm context` 这个命令，但没有任何东西告诉
agent 它存在、更没告诉它「别读整个 `site/`，那是 9k token」。产品把省 79% token 的能力
做出来了，然后没发货。

这是**同一个失败模式的第五次**——`docs/capabilities.md` §11 记着前四次（主题检查索引错位、
C-12 文件级计数、C-22 按 `<article>` 计数、回归套件不进 CI）。共同点：**验证的是零件，
不是链路**。「日志说覆盖了 2 个」验证的是计数器；「skill 写好了」验证的是文件存在。

**已修。** 我原本估计改写措辞是一件独立的内容工作。实测引用情况后这个估计偏高了：

```
AGENTS.md   8 处提到 packages/，其中 7 处是「机制层别碰」这类对装了包的站点同样成立的话
prompts/    1 处，还是 "examples/code/diagrams" 这种误命中
SKILL.md    1 处
```

做法是一份来源、两个受众：只对本仓库成立的段落用 `<!-- repo-only -->` 围起来，
`build.mjs` 在生成模板时剥掉。现在脚手架产出：

```
.ai/skills/ai-first-blogger/SKILL.md   prompts/(5)   AGENTS.md   site/  content/  ...
```

并加了发布前置检查：模板里缺任何一样、或者围栏没被剥干净，`release:check` 直接拦住。
这一条是专门针对第五次「建好了但接在空处」——**清单里的一行会被忘记，退出码不会。**

## 6. 架构合理性（技术项）

### 6.1 站得住的部分

**三平面 + 单向依赖。** `site/`（YAML/Markdown，塞不进代码）→ `content/` → `packages/`。
判据不是「谁编辑」而是「谁判断对错」，这个判据在整轮测试里没有出现例外。
`site/` 是纯数据这一点保证了它可以被 agent 安全生成——里面不可能藏 import。

**派生优于登记。** 路由从 `pages/` 目录树推导，内容类型自注册，`llms.txt` 分区从注册表派生，
示例从 `examples/` readdir 发现，`create-aifb` 的 template 在构建时从仓库生成。
metrics 的 T1/T2 就是在量这件事，本轮 0/0。手工维护的清单一定会错——这个判断在
「加了第二个 example 但 `--example` 说找不到」上已经被验证过一次。

**闸门与产物解耦。** 覆盖层能把 markup 换掉而闸门照旧生效，是因为闸门读 `dist/`，不读组件。
这让「随便改，改坏了发不出去」成为结构性质，而不是纪律。

### 6.2 站不住的部分

| 问题 | 表现 | 性质 |
|---|---|---|
| 意图/机制的线画错了两处 | `listLayout`（2.3）、社交平台名单（3.1）住在机制层 | 边界渗漏，每次都表现为「用户想要的东西没地方写」 |
| 覆盖粒度只有整页 | 改一个 class 抄 44 行 | 缺少中间粒度（slot / 布局槽） |
| 依赖框架外部的排序假设 | `enforce: 'pre'` vs `resolve.alias`（2.2） | 假设写在注释里，没有断言；Vite 改顺序就静默失效 |
| 验证的是零件不是链路 | 五次（5.1） | **这是这个项目真正的架构风险**，比任何单点设计都重要 |

最后一条的应对已经写进 `docs/capabilities.md`：新增能力的验收标准改为
**「能不能写出一条从输入到 `dist/` 的断言」**。写不出来，就说明它还没接上。
本轮三个新场景就是照这条做的。

## 7. 与用户规划文件的耦合（产品项）

问的是：用户自己写的东西（提示词、skill、模板、YAML）和产品之间黏得有多紧。

| 用户产物 | 耦合方向 | 评价 |
|---|---|---|
| `site/*.yaml` | 引擎读它，它不读引擎 | ✅ 单向。示例站换掉全部 7 个文件，引擎零改动 |
| `site/voice.md` | frontmatter 被 analyze 读；正文被 agent 读 | 🟡 前者耦合清晰；**后者和产品零耦合**（4.2） |
| `site/themes/*.css` | 引擎通过虚拟模块拿，包不知道文件怎么摆 | ✅ 方向正确；但可表达范围不够（2.1） |
| `site/templates/*.astro` | 存在即生效，无需注册 | 🟡 机制好；覆盖时要 `import` 引擎的 `@layouts` / `@lib`——**用户文件依赖了机制层的内部路径**（2.3） |
| `.ai/skills/` · `prompts/` | ——— | ❌ **不在交付物里**（5.1） |

### 7.1 唯一的反向耦合，和它的代价

`site/templates/` 里的覆盖文件必须 `import PageLayout from '@layouts/PageLayout.astro'`、
`import { itemListSchema } from '@lib/schema'`。**用户文件引用了机制层的内部符号**，
这是整个架构里唯一一处反向依赖。

它是必要的（不然覆盖页面就要自己拼 JSON-LD 和 head），但代价真实：这些别名不是公开 API，
引擎重构 `schema.ts` 时不会有任何东西提醒有 68 行用户代码在用它。
`docs/specs/templates.md` 现在列了「覆盖仍须满足什么」（C-01/C-07/C-10/C-16/C-17/C-21/C-22/C-23），
但没有列「你可以依赖哪些导入」。**覆盖层需要一份公开 API 清单**，否则它是一份没有边界的承诺。

### 7.2 产品判断

意图层的耦合设计是对的，而且经住了一个「和默认审美相反」的站的检验：换掉全部意图文件 +
3 个模板覆盖 + 1 个主题，引擎一行没动，闸门照常拦截。

真正的产品缺口不在耦合太紧，在**该交付的没交付**：用户参与的那一层——skill、prompts、
AGENTS.md——是这个产品区别于「又一个 Astro 主题」的全部理由，而它现在只存在于开发仓库里。

## 8b. 评估之后的优化轮

上面「本轮不修」的四项，重新估过成本后全部做掉了——其中两项我原先估贵了。

| 项 | 结果 |
|---|---|
| agent 契约进脚手架 | 围栏剥离 + `build.mjs` + `release:check` 前置检查 |
| `listLayout` 收口 | `stack` 进枚举 + 取值校验 + 删掉示例的 68 行覆盖 |
| `voice.md` 篇幅可声明 | 三组阈值（正文宽度 / 小标题数 / 列表占比），默认全部惰性 |
| 覆盖层公开 API | [ADR 0004](./adr/0004-template-api.md) + `templates.md` 清单 |
| 版本 | 三个包 0.2.0，`release:check` 通过（未发布） |

回归从 16 个场景到 **19 个**，新增：列表布局从 YAML 生效 / 非法取值按名字报错 /
voice 声明的篇幅被计分且未声明时惰性。

**voice 阈值默认惰性**这一点值得单独说：新增一个计分维度如果出厂就生效，等于悄悄改写
每个既有站点的历史分数。一份没声明长度的 voice，就是没同意过任何长度。

示例站顺带补齐了：五篇文章原先 1739–2492 列，全部低于它自己声明的 3000。补的不是字数，
是每篇里被略过的那一段——试过什么没成、代价具体多少、什么场景下不该这么做。
现在 3056–3742 列，分数 100，且这次的 100 是有含义的。

**仍然不做**

- token 形状层（`--radius` 等 80 处硬编码）——覆盖层已经把这个需求的出口堵上了，
  改动会牵动 C-12/C-13 和四份主题文件，收益/风险比不划算。记为**有意不做**。
- 覆盖层的 slot 机制——真实需求样本目前为 0

## 9. 一句话

模板层和 SEO 层在被一个「反着来」的站认真使唤之后是立得住的，**代价是发现了两条闸门看不见的
缺陷和一处从未生效的覆盖路径**；产品最大的缺口不在这些，而在于**「AI 优先」的那一半——
skill 和 prompts——根本没随包发出去**。那一半现在发出去了。

留下的方法论比修的四个 bug 更值钱：**「能力建好了但接在空处」已经五次，共同点是验证的是
零件不是链路。** 所以新增能力的验收标准现在是一句话——能不能写出一条从输入到 `dist/`
（或到退出码）的断言。写不出来，它就还没接上。
