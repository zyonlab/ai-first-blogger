# Internationalisation

Two separate things share this word, and keeping them apart is the whole design:

```
UI chrome        packages/engine/i18n/<locale>.ts    "7 min read", "Skip to content"
Site content     site/*.yaml, content/**             everything a reader came for
```

The first is the framework's own strings, translated once for everybody. The
second is yours, and a new owner **rewrites** it rather than translating it —
which is why it lives in `site/`. The dividing line is in
[`site-config-contract.md`](./site-config-contract.md#the-dividing-line-chrome-vs-content).

## One language

The default, and the whole story for most sites:

```yaml
# site/site.yaml
locale: zh-CN
```

One language, no prefix, no `hreflang`, `<html lang="zh-CN">`. Adding a language
is opt-in and a site that never does gets output byte-identical to a site built
before the option existed.

## More than one language

The default language keeps the root and every other one is served behind a
prefix — the shape Astro's own i18n routing uses, and the one Google's
documentation describes:

```yaml
locale: zh-CN        # the default: served at the root, with no prefix
locales:             # every locale, including the default; value = URL segment
  zh-CN: zh
  en-US: en
```

```
/            /writing/       /topics/x/      zh-CN
/en/         /en/writing/    /en/topics/x/   en-US
```

Every locale needs a message table in `packages/engine/i18n/` — the build fails
by name if one is missing. The default locale declares a prefix it never uses in
a URL: `hreflang` and the sitemap both need to name it.

Rationale, and the decisions behind each part:
[`../adr/0006-i18n-routing.md`](../adr/0006-i18n-routing.md).

### Where a translation lives

```
content/posts/why-retries-made-it-worse.mdx      zh-CN — the default language
content/posts/en/retries-made-it-worse.mdx       en-US — under the URL prefix
```

The directory is the URL prefix, so a file is in the language its path says it
is. Two optional frontmatter fields, added to every content type:

| Field | Default | When you write it |
|---|---|---|
| `locale` | the directory, else the site's default | to contradict the path |
| `translationKey` | the entry's `slug` | on a translation whose slug is localised too |

```yaml
# content/posts/en/retries-made-it-worse.mdx
slug: retries-made-it-worse
translationKey: why-retries-made-it-worse   # pairs it with the Chinese article
```

A translation that keeps the original slug needs neither field. `translationKey`
is what produces the `hreflang` pair, and it is the *only* thing that does — a
localised slug is a good idea and it means the pairing cannot come from the path.

### Not every article exists in every language

That is the point, and it is enforced rather than assumed:

- An article that exists only in Chinese produces **no** English page and emits
  **no** `hreflang`.
- A topic, series or listing page is built for a language that has at least one
  entry in it. An empty English "Writing" section is not a smaller site; it is a
  page whose entire content is "nothing here yet", in a language the reader did
  not ask for.
- Fixed pages (`/about/`, `/uses/`, …) exist in every declared language. They are
  copy, and declaring a language claims you serve them in it.
- `/404` and `/robots.txt` get no prefix. A host serves one 404 and a crawler
  reads one robots.txt.

C-30 fails the build if any of that stops being true — an `hreflang` pointing at
a page nobody built is a soft 404 with a reference from the page it is
impersonating, and it is invisible from inside the build.

### Copy, per language

Any mapping in `site/` may carry an `i18n:` block. It replaces that mapping's own
keys for the locale named:

```yaml
# site/taxonomy.yaml
topics:
  llm-reliability:
    title: 可靠性与降级
    description: 模型会超时、会改主意、会编。
    pillar: foundations
    i18n:
      en-US:
        title: Reliability and fallbacks
        description: The model times out, changes its mind, and makes things up.
```

The same block works in `site.yaml` (title, description, hero, services, nav),
`pages.yaml` (whole sections), `content-types.yaml` (labels and list copy) and
`taxonomy.yaml` (topic and series titles and descriptions).

- Mappings merge key by key, so a locale states only what differs.
- Lists and scalars replace whole. Half-translating a nav bar by index is not a
  thing anyone means.
- What a locale leaves out renders in the default language, and C-31 warns about
  it. That is deliberate: a section should be able to go live before every string
  in it has.

**Not localisable, on purpose:** a topic's slug, its pillar and its membership; a
content type's `route`. Those are structure. One route per type keeps `/writing/`
and `/en/writing/` parallel, so a page's translation is derivable from its own
URL. An individual entry's slug *is* free to differ — that is what
`translationKey` is for.

### The sitemap

```js
// astro.config.mjs
import { engine, sitemapOptions } from 'aifb-engine';
sitemap(sitemapOptions())
```

`{}` until the site declares a second locale, and then the `i18n` block
`@astrojs/sitemap` needs. It pairs URLs that are identical apart from the prefix
— the roots, the listings, the fixed pages — and cannot pair an article whose
English slug differs from its Chinese one. That article is paired by the
`<link rel="alternate">` tags in its head, which Google treats as an equivalent
signal rather than an additional one.

Under a mount the option does nothing: `@astrojs/sitemap` reads the locale out of
the first path segment, which under a mount is the mount. The build says so.

### With a mount

Mount outside, locale inside:

```js
engine({ mount: '/blog' })   // + locales: { zh-CN: zh, en-US: en }
```

```
/blog/       /blog/writing/       zh-CN
/blog/en/    /blog/en/writing/    en-US
```

The mount is where the *host* put the engine; the locale prefix is the engine's
own partition inside it. The reverse — a site whose host is bilingual and mounts
a single-language engine at `/zh/blog/` — is what 0.3.0 already did, and such a
site should **not** also declare `locales`: the language is already in the mount,
and declaring it twice produces `/zh/blog/zh/`.

### Template overrides

A page override under `site/templates/pages/` becomes a dynamic route once a
second locale exists, so it needs paths:

```astro
---
import { localeStaticPaths, localeOfPath } from '@config/routes';
export const getStaticPaths = localeStaticPaths;
const locale = localeOfPath(Astro.url.pathname);
---
```

Astro refuses to build a dynamic route with no paths, so forgetting this fails
the build rather than shipping something wrong. A single-language site needs no
change at all. See [`templates.md`](./templates.md).

## Adding a chrome locale

1. `cp packages/engine/i18n/zh-CN.ts packages/engine/i18n/fr-FR.ts`
2. Replace the first line with `import type { MessageTable } from './types';` and
   change the export to `const messages: MessageTable = { … }; export default messages;`
3. Register it in `locales` in `packages/engine/i18n/index.ts`.
4. Use it: `locale: fr-FR`, or a row in `locales:`.
5. `pnpm check` — any missing key is a type error naming the key.

## Missing translations are a compile error

`en-US.ts` is declared `const messages: MessageTable`, and `MessageTable` is
`Record<MessageKey, MessageValue>` where `MessageKey` is derived from the
reference locale. Dropping or misspelling a key fails `pnpm check`.

This is the guarantee that matters for the chrome: adding a locale cannot
half-succeed. Site copy is the opposite by design — it falls back and is
reported, because a half-translated site should be publishable.

## In a component

```astro
---
import { localeOfPath } from '@config/routes';
import { messages } from '@i18n/index';

const locale = localeOfPath(Astro.url.pathname);
const t = messages(locale);
---
<strong>{t('toc.title')}</strong>
<span>{t('article.readingTime', { minutes: 7 })}</span>
```

The locale comes from the page's own URL, not from a module-level constant: a
static build renders pages concurrently through one module registry, so a mutable
"current locale" is a page rendering in whichever language finished last.

`t` imported directly is still available and is bound to the site's default
locale — correct for anything outside a render, wrong inside one on a bilingual
site.

- `{name}` placeholders are interpolated from the second argument.
- A message may be a `string` or a `string[]`; arrays are joined with newlines,
  which is how the multi-line AI study prompt is stored.

## What follows the locale automatically

`<html lang>` · `og:locale` and `og:locale:alternate` · `inLanguage` in every
JSON-LD block · `Intl.DateTimeFormat` · `hreflang` and `x-default` · the sitemap's
`i18n` block · one `/rss.xml` and one `/llms.txt` per language.

## Enforcement

`pnpm metrics` (T1) scans `packages/engine/components/`, `packages/engine/pages/`,
`packages/engine/layouts/` and `packages/engine/lib/` for natural-language copy
and locale literals in code, and reports the offending files. Target is zero.

```bash
pnpm metrics
# ✓ T1 reuse            0 file(s) block a rebrand (target 0)
```

`pnpm validate` adds C-30 and C-31; both are silent on a single-language site.
