# Internationalisation

UI chrome lives in `packages/engine/i18n/`. Site content does not.

## What belongs here

Only text the framework emits regardless of what the site is about:

```
On this page · Published {date} · 7 min read · Copy prompt · Skip to content
Key takeaways · All Writing · Page not found
```

Site-specific copy — the About page, the Uses table, topic descriptions, content type
labels — lives in `site/` because a new owner **rewrites** it rather than
translating it. The rationale is in
[`site-config-contract.md`](./site-config-contract.md#the-dividing-line-chrome-vs-content).

## Structure

```
packages/engine/i18n/zh-CN.ts    reference locale — defines the key set
packages/engine/i18n/en-US.ts    checked against the reference at compile time
packages/engine/i18n/types.ts    MessageKey / MessageTable, derived from the reference
packages/engine/i18n/index.ts    t(), activeLocale, ogLocale
```

The active locale is `site.locale`. A locale with no message table fails the build
with instructions rather than falling back silently.

## Usage

```astro
---
import { t } from '@i18n/index';
---
<strong>{t('toc.title')}</strong>
<span>{t('article.readingTime', { minutes: 7 })}</span>
```

- `{name}` placeholders are interpolated from the second argument.
- A message may be a `string` or a `string[]`; arrays are joined with newlines, which
  is how the multi-line AI study prompt is stored.

## Missing translations are a compile error

`en-US.ts` is declared `const messages: MessageTable`, and `MessageTable` is
`Record<MessageKey, MessageValue>` where `MessageKey` is derived from the reference
locale. Dropping or misspelling a key fails `pnpm check`.

This is the guarantee that matters: adding a locale cannot half-succeed.

## Adding a locale

1. `cp packages/engine/i18n/zh-CN.ts packages/engine/i18n/fr-FR.ts`
2. Replace the first line with `import type { MessageTable } from './types';` and
   change the export to `const messages: MessageTable = { … }; export default messages;`
3. Register it in `locales` in `packages/engine/i18n/index.ts`.
4. Set `locale: 'fr-FR'` in `site/site.yaml`.
5. `pnpm check` — any missing key is a type error naming the key.

`activeLocale` also drives `<html lang>`, `Intl.DateTimeFormat`, `inLanguage` in
JSON-LD and `og:locale`, so those follow automatically.

## Adding a key

1. Add it to `packages/engine/i18n/zh-CN.ts` (the reference).
2. `pnpm check` now fails for every other locale until they define it. That is the
   intended behaviour.

## Enforcement

`pnpm metrics` (T1) scans `packages/engine/components/`, `packages/engine/pages/`, `packages/engine/layouts/` and
`packages/engine/lib/` for natural-language copy and locale literals in code, and reports the
offending files. Target is zero.

```bash
pnpm metrics
# ✓ T1 reuse            0 file(s) block a rebrand (target 0)
```

## Not covered

Multi-locale sites — serving `/en/` and `/zh/` from one build — are out of scope.
This layer makes the framework **locale-neutral**, so one site can be built in one
language. Per-URL locale routing would need routes, hreflang and per-locale content
collections; open a new ADR if it becomes a requirement.
