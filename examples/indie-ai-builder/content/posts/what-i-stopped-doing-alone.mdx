## 结论先说

一个人做产品的头半年，我照搬了上一份工作的全套工程实践。后来停掉了四件：PR 自审、
分支策略、覆盖率目标、方案文档。留下了两件：可观测性和自动化检查。

判断标准只有一条：**这件事解决的是「人和人之间的信息差」，还是「我和未来的我之间的
信息差」。** 前者在一个人的项目里不存在。

## 停掉：给自己开 PR 然后自己批

我做过三个月。每次都认真写描述、认真读 diff、认真点 approve。

它唯一起作用的一次，是我在写描述时发现自己讲不清这个改动为什么必要——于是删了。但那个
价值来自「被迫解释一遍」，不是来自 PR 这个形式。现在我用一句 commit message 达到同样的
效果，成本从十分钟降到二十秒。

## 停掉：分支策略

`develop` / `release` / `hotfix` 这套是为了让多个人的工作不互相踩。一个人不会踩自己。

现在只有 main 和临时分支。真正保护我的是「validate 不过不许部署」，不是分支的名字。

## 停掉：覆盖率目标

我曾经把覆盖率卡在 80%。为了那 80%，我给一堆纯搬运的函数写了断言 `expect(x).toBe(x)`
级别的测试。它们从来没红过，也从来没救过我。

现在我只测两类东西：**算钱的**和**判断对错的**。加起来覆盖率大概 40%，但每一条都对应
一次真实出过的问题。

## 停掉：写方案文档再动手

团队里方案文档是为了在动手前对齐。一个人没什么好对齐的，而且我发现自己写的方案文档
有一半在动手第二天就作废了——**我对问题的理解本来就来自动手**。

现在的做法是先写一个能跑的最小版本，再回头写一段「为什么是这样」放进代码注释或者
这个博客。文档从「事前的猜测」变成了「事后的结论」，准确率高得多。

## 留下：可观测性

这条不但留下，还加强了。团队里出事有人帮你看，一个人出事只有你。

我现在的规矩是：**任何一个能花钱的调用，必须能回答「谁、什么时候、花了多少」**。
重试策略也是靠这条规矩才算得清，见[重试从 3 次提到 5 次](/writing/retries-made-it-worse/)。
这条规矩是踩过坑之后立的，过程写在[超时不等于没花钱](/writing/timeout-is-not-free/)。

## 留下：自动化检查

理由和上面一条相同：它替代的不是同事，是**未来那个已经忘了细节的我**。

评测集是这里面收益最高的一项，前提是它得跑得动——这件事我单独写过，见
[把评测集砍到 300 条之后](/writing/cutting-the-eval-set/)。

## 停错过一件：变更记录

上面四件我到现在都没后悔。但同一轮里我还停掉了第五件，那件是错的。

我停掉了写变更记录，理由和方案文档一样——没人要看。四个月后我在排查一个「什么时候开始
变慢的」问题，翻 git log 翻了两个小时，因为 commit message 只说了改什么，没说为什么改，
更没说改完之后哪个数字动了。

**方案文档和变更记录看起来是同一类东西，其实方向相反。** 方案文档是写给动手之前的我，
而我对问题的理解来自动手，所以它天然会过期。变更记录是写给三个月后的我，那时候我唯一
的信息来源就是它——它不但不会过期，还是唯一不会过期的东西。

我当时的判断标准（「解决人和人之间的信息差，还是我和未来的我之间的信息差」）本来就能
分出这两者，我只是没有对第五件用这个标准，而是顺手把它归进了「文档」这一类。

现在的做法很轻：每个会影响成本或延迟的改动，在 commit message 里补一行「改之前 X，
改之后 Y」。二十秒，四个月后值两小时。

## 一个反例

这四件事我都是在**做过一段时间之后**才停的，不是一开始就跳过。分支策略那件事，我是在
一次误删本地改动之后才真的理解它在防什么，然后才有把握说「这个风险我用别的方式覆盖了」。

先做，再判断值不值得——这个顺序反过来就是在凭想象砍流程。

**什么时候不该照抄这篇。** 只要项目里出现第二个人，上面停掉的四件里有三件要立刻加回来：
PR 是为了让另一个人能看懂改动，分支策略是为了两个人不互相踩，方案文档是为了动手前对齐。
它们的代价在一个人时是纯损耗，在两个人时是最便宜的沟通方式。

覆盖率那条我不会加回来——它衡量的从来不是「测得对不对」，只是「测了多少行」。
