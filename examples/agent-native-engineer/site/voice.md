## 这个站怎么写

每篇从一次真实的线上问题开始：当时看到什么、以为是什么、最后是什么。没有具体问题
就不要写。

**结论写在第一段。** 读者是同行，不需要「什么是 Agent」的铺垫，需要的是「它在什么
情况下会咬你」。

**带上数字。** 这个领域最容易写成感觉。延迟就给毫秒，成本就给美元和 token 数，
可靠性就给失败率。没有数字的判断在这里等于没有判断。

**讲代价。** 每个方案都有它变坏的场景。只讲收益的文章读起来像发布会——而且读者会在
自己的账单上把代价找出来。

**不写没跑过的东西。** 拿不准就说拿不准。「我没查明白为什么它第三轮会改主意」是合法
的结尾，「综上所述，Agent 代表了软件的未来形态」不是。

## 怎么改这份文件

上面的正文是给写作的 agent 读的——它决定语感，脚本读不懂。
frontmatter 里的 `signals` 是给 `pnpm analyze` 读的——它只能识别机械痕迹。

两者是分工，不是重复：短语表永远判断不了「这段话有没有信息量」，正文也永远变不成
退出码。想换一种口吻，就改这个文件。

风格分数**不阻断发布**（`site/policy.yaml` 的 `style.minScore` 默认为 null）。
它是一个指向「这几段值得重写」的指针，不是判决。
